# 统一驾驶台：地图、手动遥控与未来任务下发

日期：2026-10-25。当前硬件位流：BTD6/SIN1 系列（当前 PID 修正版 User Code `0x53494E31`）。本文件描述统一驾驶台的可复现操作、传感器状态显示和动态障碍仿真边界。

## 1. 当前可复现的界面

在电脑 PowerShell 运行：

```powershell
cd E:\gowin\ling_shu_vision
python .\fpga\motor_bt_drive\pc_unified_console.py --port COM9
```

若实际蓝牙串口不是 COM9，以设备管理器枚举端口替换。一个 GUI 窗口同时提供：

- 2 m × 2 m、20 × 20 格地图；点击或输入 `(x,y)` 后用 `config/nav-map-2m.json` 和 `scripts/build_nav_map.py` 的同源占据与 BFS 做**本机路线预览**；障碍格拒绝、起点固定 `(18,1)`；
- BTD6 蓝牙 COM9 9600/8N1 手动前/后/左横移/右横移、12/16/20 计数每 10 ms 三档速度、停止 `S`；支持“按住运行”和“点击锁定/再点停止”两种操作模式，方向切换自动插入 140 ms 中性停车，减少必须重复点击的问题；
- FPGA 通过蓝牙返回的 `M1`～`M4` 诊断行、COM 状态和本地写入字节数；**打开串口/本地写入不是 FPGA ACK**；
- 自动导航模式与安全停车模式互斥；导航按钮只有在 BTD6 位流、地图/权限确认和导航模式同时满足时开放。COM6 可接收 `I0 T1 D0110 H1` 状态行，GUI 显示 IMU/ToF 有效性、距离和硬停车，并在导航模式首次收到 `H1` 时发送停止。
- “仿真 ToF 障碍并重规划”只做本机验证：把路径前方格加入动态占据图，再从当前格 BFS 到原目标；实际 FPGA 仍以 ToF 门控停车，替代路径必须由 GUI 重新下发。

连接不会自动允许运动。人工确认 BTD5、确认四轮离地并勾选后，按住方向键每 100 ms 刷新；松开/失焦/取消许可发送 `S`。发送故障时 GUI 断开并要求人工关闭驱动板 12 V。此界面继承了原遥控的离地边界，**不是已准许落地驾驶或无人导航的程序**。原 `pc_bt_control_btd4.py` 保持不变，可作为回退。

离线验证：

```powershell

python -m py_compile fpga/motor_bt_drive/pc_unified_console.py fpga/motor_bt_drive/pc_unified_model.py
python -m pytest -q tests/test_pc_unified_model.py tests/test_nav_goal_api.py
```

2026-10-25 结果：GUI 语法检查通过，导航/ToF/传感器/动态障碍回归 `16 passed`；仿真输出 `PASS nav obstacle stop + replan`。这不等于落地实车已完成绕障验收；上板下载仍需先确认 12 V 关闭、四轮离地和 JTAG 连接。

## 2. 为什么不能立即把旧 Pi 终点功能接入 BTD5

旧路径：浏览器 → Pi HTTP `/api/nav/goal` → Pi USB 串口 → FPGA NAV3 LED 预览位流。旧位流只识别目标并点 LED，不连接电机，也没有回执。当前 BTD5 则从蓝牙 COM9 接收单字节 `F/B/L/R/S/1/2/3`；它没有 NAV3 目标解析、导航模式、路径执行或目标 ACK。两个独立位流不可能在同一 FPGA 上作为“一个完整系统”同时运行。**绝不能把 NAV3 的二进制目标帧直接送入 BTD5 蓝牙口：其中偶然出现的 ASCII 方向字节可能被旧解析器当成遥控命令。**

## 3. 最终版采用的单一驾驶台链路

```text
统一电脑 GUI ─ 蓝牙 SPP/COM9 ─ 新 FPGA 控制/状态协议 ─ 模式仲裁 ─ FPGA BFS/路点跟踪 ─ 四轮 PI
      │                         └─ FPGA ACK/进度/位姿/故障/四轮速度回传
      ├─ 本地地图预览（仅供人看；不下发整条路线）
      └─ Pi 摄像头/红瓶识别画面（只读或视觉目标，不负责基础导航运动）
```

正式版 GUI 使用同一 COM9 双向连接发送**模式、目标、任务意图**，FPGA 根据地图版本与当前位姿规划；Pi 不再是“手动选终点”的必经网关。Pi 可独立传视觉识别结果，但只作为有时间戳的感知输入。若比赛时电脑不在车旁，接收一次合法 AUTO 目标后 FPGA 仍须能自主执行，期间保留物理 S0 急停、ToF 安全停机、编码器故障停机；无线断链时的 AUTO 策略须专门仿真和实测，不能照搬手动 300 ms 看门狗。

控制报文需固定版本、长度、序号、地图 ID、命令类型、参数和 CRC；目标范围/障碍占据/地图版本不符时拒绝。回传至少区分 `RECEIVED`、`REJECTED`、`PLANNED`、`EXECUTING`、`BLOCKED`、`ARRIVED`、`FAULT`，携带原序号与当前路点/位姿/故障原因。GUI 必须把“本地写入成功”“FPGA 已确认”“实际到达”分开显示。手动/AUTO/视觉任务互斥；切换模式先停车并清 PI 历史量。任务和速度命令不能直接写 PWM。

## 4. 开放任务按钮前的硬门槛

1. 完成新 FPGA 顶层：保留 BTD5 四轮闭环，增加版本化双向命令解析、ACK、模式仲裁、当前起点 BFS、路点跟踪、ToF 安全门控、IMU 航向与失联处理；补定点旋转。
2. 完成 ModelSim 协议/路径/模式抢占/看门狗/障碍/复位测试，以及 Gowin 全量管脚、资源和时序检查；保存位流哈希与 User Code。
3. 电机 12 V 关闭时下载 SRAM：GUI 建链后先读取 FPGA `HELLO`/版本与能力字段，**只有版本匹配才显示任务按钮**；NAV3/BTD5/未知位流一律禁发。
4. 四轮离地实测 GUI→FPGA ACK、规划、执行状态；确认急停/失联/障碍停机。再做低速落地与多次到达、绕障统计。未完成前不写 Flash。

现在最优先的下一项代码工作不是改旧 Pi HTTP 下发，而是**新的 FPGA 控制协议与模式仲裁**。这决定一个 GUI 能否真正同时具备导航、任务下发与手动驾驶，而不是只把三个按钮画在一起。
